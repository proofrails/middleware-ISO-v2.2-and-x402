x402 payment-gated actions

The hosted ProofRails x402 path uses Flare mainnet. A successful request spends real USD₮0 and creates irreversible blockchain transactions. Verify the chain, token, facilitator, recipient, amount and fee policy before signing.

ProofRails can require payment before executing selected API actions. A successful hosted request records the payment, hashes the delivered API result, returns a receipt reference and creates a signed evidence bundle whose current hash is anchored on Flare.

ProofRails operates an integrated x402 facilitator for its own payment-gated APIs; on Flare, USDT0 settlement uses the ProofRails X402Facilitator contract.

The current verified addresses and chain parameters are listed in Networks and contracts.

Standard client exchange

The hosted paid FX endpoint completed this exchange with unmodified @x402/fetch and @x402/evm version 2.19.0:

  1. The client sends the original API request.
  2. ProofRails returns HTTP 402 with PAYMENT-REQUIRED.
  3. The client signs the selected Flare USD₮0 authorization.
  4. The client retries the same request with PAYMENT-SIGNATURE.
  5. ProofRails settles through X402Facilitator and returns the protected HTTP 200 response.
  6. PAYMENT-RESPONSE identifies the settlement and the ProofRails receipt.
  7. The receipt pipeline packages the evidence and anchors the current bundle hash.

See x402 compatibility and the mainnet proof walkthrough.

Current source adapters

The source tree also contains native FLR and Base USDC verification paths. They have not passed the same published evidence gate and should be treated as experimental until each path has its own transaction, delivery, receipt and anchor evidence.

Premium actions

The hosted OpenAPI is the runtime source for available routes. Current source includes paid actions for bundle verification, statement generation, ISO retrieval, FX lookup, bulk verification and refund handling. Authorization and deployment availability vary by route.

Local mock mode

X402_MOCK_PAYMENTS=true

Mock mode skips onchain verification. Use it only for local development and automated tests. A mock success is not payment evidence, and production configuration must keep mock payment mode disabled.
