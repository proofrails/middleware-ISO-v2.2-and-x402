# Security and limitations

## Key handling

- Keep API keys and signing keys server-side.
- Use a secret manager and inject secrets at runtime.
- Never commit `.env`, private keys or bearer tokens.
- Separate development, staging and production credentials.
- Give worker, API and deployment identities only the permissions they require.
- Rotate exposed keys and keep signing-key rotation history.

The current source's agent anchoring configuration accepts private-key input. Review that implementation before production use. Secret storage should use authenticated encryption or an external signing service rather than reversible encoding.

## Hosted and source drift

The source repository and hosted API can differ. Generate clients from the hosted OpenAPI, pin tested behavior and verify the exact deployed commit before a release. A source route is not a hosted capability until runtime discovery or a live test confirms it.

## Evidence boundary

ProofRails establishes integrity relationships among receipt data, delivered-resource hashes, generated files, signatures, bundle hashes and onchain commitments. It does not independently validate every business fact supplied to it.

An onchain anchor proves the integrity and timing of the committed hash. It does not prove the truth or legal sufficiency of the underlying offchain data.

## ISO boundary

ProofRails generates ISO 20022-style artifacts. Several generators are minimal or best-effort. Validate XSD, market-practice and semantic requirements for the institution or network that will consume an artifact. The message family or namespace alone does not establish compliance or certification.

## Credential-envelope boundary

The source credential helper can fall back to an unsigned `alg: none` envelope when Ed25519 dependencies or a signing key are unavailable. Reject unsigned envelopes in production and do not describe them as verifiable credentials. The verified July 2026 standard-x402 receipt served `vc.json` as `null`; no credential claim is attached to that evidence pack.

## x402 boundary

The hosted Flare USD₮0 path has completed a standard x402 2.19.0 client flow through payment, protected result, receipt, signed bundle and matching anchor. This evidence applies to that exact hosted path.

Native FLR and Base USDC paths exist in source but have not passed the same evidence gate. Treat them as experimental. ProofRails does not expose a generic public `/verify` and `/settle` facilitator service for third-party merchant APIs.

The exact-client lifecycle should remain covered by a durable committed regression test. The July acceptance run used an external regression harness because the repository did not yet contain that complete test.

## Receipt completion and anchoring

A hosted receipt is complete only after its current bundle hash is anchored. Settlement can succeed before delivery, receipt generation, bundle creation or anchoring finishes. Keep the receipt in its actual intermediate or failed state and do not report completion early.

## Mainnet safety

The current hosted x402 USD₮0 path uses Flare mainnet and real value. Verify the chain, token, facilitator, recipient, amount, validity window and fee policy before signing. The payment interface should display an unavoidable mainnet warning before a user can authorize payment.
