# Agent workflows

Agents need evidence for more than the transfer itself. A useful receipt records what the agent paid, which resource or API it requested, what result identifier it received and which evidence was committed.

## Purchase receipt pattern

```text
agent chooses resource
→ payment authorization or transaction
→ merchant/facilitator settles
→ service returns resource identifier
→ ProofRails creates receipt
→ bundle records payment + workflow context
→ bundle hash is anchored
```

Recommended receipt metadata:

```json
{
  "agent_id": "agent-uuid",
  "task_id": "research-0042",
  "endpoint": "/premium/data",
  "resource_id": "dataset-2026-07",
  "payment_id": "0x...",
  "result_hash": "0x..."
}
```

Only include a `result_hash` if it is computed over the exact delivered bytes or canonical result object. A URL or label is not a content commitment.

## Read and verify

Agents can:

- list receipts with cursor pagination;
- use lightweight status polling when available;
- fetch receipts and anchors;
- verify bundle URLs, hashes or CIDs;
- retrieve ISO-style artifacts;
- create refund evidence;
- query x402 payments and revenue where authorized.

## Anchor arbitrary task data

Current source supports canonical JSON hashing:

```http
POST /v1/agents/{agent_id}/anchor-data
```

Use this for non-payment evidence such as task completion, data provenance or model-output commitments. The raw `data` object is hashed; the anchor record stores the hash, not the supplied object.

## Delivery and retries

Use idempotency keys for writes. Prefer signed webhooks for terminal events, SSE for live UI updates and 2–5 second polling only as a fallback. Never let an agent retry a value transfer merely because a receipt or callback timed out; reconcile payment state first.
