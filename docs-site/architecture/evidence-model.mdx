# Evidence and trust model

ProofRails uses two complementary integrity mechanisms:

1. an Ed25519 signature over a canonical manifest; and
2. an onchain commitment to the SHA-256 of the evidence ZIP.

<img src="/assets/evidence-model.svg" alt="ProofRails evidence bundle and onchain trust model" />

## Bundle contents

A normal evidence ZIP contains:

```text
manifest.json
manifest.sig
public_key.pem
pain001.xml
receipt.json
tip.json
```

Configuration can add files such as credential or IVMS data. Post-processing APIs can also expose additional ISO XML beside the bundle. The manifest lists each committed file with its byte count and SHA-256.

## Verification procedure

A verifier should:

1. download the exact bundle bytes;
2. compute `SHA-256(evidence.zip)`;
3. parse the ZIP and reject CRC or path errors;
4. canonicalize `manifest.json` exactly as the producer does;
5. verify `manifest.sig` using `public_key.pem`;
6. recompute every manifest file hash and byte count;
7. compare the bundle hash with the receipt API;
8. compare it with the EvidenceAnchor event on the expected chain and contract.

## Claims this supports

A passing verification supports the statement:

> These exact bundle bytes match the receipt record and the hash committed by the identified anchor transaction, and the included manifest signature validates against the included public key.

It does not independently establish:

- legal settlement finality;
- invoice validity or commercial performance;
- ownership of a wallet;
- KYC, AML or sanctions status;
- correctness of user-supplied metadata;
- bank acceptance or ISO certification;
- exact delivery bytes unless their hashes appear in the committed manifest.

## Key provenance

An included public key proves internal signature consistency, not the external identity of the signer. Production deployments should publish a trusted signing-key fingerprint, rotation policy and revocation history through a separately authenticated channel.
